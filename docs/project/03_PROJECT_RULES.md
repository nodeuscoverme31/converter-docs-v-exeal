# CORE

## RULE-SOT-001 — Источник истины определяется типом вопроса

**ПРАВИЛО:**  
Не использовать один документ, старый чат или память модели как универсальный источник истины. Для каждого вопроса использовать источник, который за него отвечает.

**ЗАЧЕМ:**  
Предотвращает ситуации, когда старый контекст, handoff или предположение перебивает более свежий и проверяемый источник.

**КОГДА ДЕЙСТВУЕТ:**  
При любом анализе, изменении проекта, проверке требований, статуса реализации или результата.

**НЕ ТРЕБУЕТ:**  
Перечитывать весь проект перед каждым небольшим действием. Проверяется только релевантный источник.

**ИСТОЧНИК:**  
PROJECT-RISK / EXTERNAL-PRACTICE

---

## RULE-VERIFY-001 — Проверка перед утверждением результата

**ПРАВИЛО:**  
Не заявлять `готово`, `работает`, `PASS`, `исправлено`, `данные сохранены`, `без потерь` или другой проверяемый результат без свежего evidence, достаточного именно для этого утверждения.

**ЗАЧЕМ:**  
Главный риск проекта — ложноположительный результат, особенно когда Excel создан, но часть данных потеряна или изменена.

**КОГДА ДЕЙСТВУЕТ:**  
При проверяемых утверждениях о состоянии реализации, тестах, конвертации и качестве результата.

**НЕ ТРЕБУЕТ:**  
Запускать полный regression suite для обычного обсуждения или гипотезы.

**ИСТОЧНИК:**  
SPEC / PROJECT-RISK / EXTERNAL-PRACTICE

---

## RULE-SCOPE-001 — Не расширять MVP молча

**ПРАВИЛО:**  
Не добавлять новые функции, требования, форматы, платформы или пользовательские сценарии в текущий MVP без явного решения owning phase.

**ЗАЧЕМ:**  
Предотвращает расползание маленького Word → Excel инструмента в универсальный офисный конвертер.

**КОГДА ДЕЙСТВУЕТ:**  
При предложениях и изменениях, которые выходят за подтверждённый `02_MVP_SPEC.md`.

**НЕ ТРЕБУЕТ:**  
Запрещать полезные идеи. Их можно предложить и сохранить как `Позже`, не включая в MVP.

**ИСТОЧНИК:**  
INTENT / SPEC / PROJECT-RISK

---

## RULE-REUSE-001 — Проверять готовое до изобретения нового

**ПРАВИЛО:**  
Перед существенным новым решением соответствующая фаза должна проверить существующие продукты, официальные возможности, open-source и пригодные компоненты. Найденное не считается выбранным до проверки и принятия owning phase.

**ЗАЧЕМ:**  
Часть Word → Excel задачи уже решена существующими инструментами; повторная реализация без проверки увеличивает стоимость и риск.

**КОГДА ДЕЙСТВУЕТ:**  
Перед выбором существенного технического или продуктового решения.

**НЕ ТРЕБУЕТ:**  
Бесконечного исследования или принятия open-source только потому, что он существует.

**ИСТОЧНИК:**  
INTENT / PROJECT-RISK / EXTERNAL-PRACTICE

---

## RULE-WRITE-001 — Проверять цель перед изменением

**ПРАВИЛО:**  
Перед действием, которое меняет код, файл, repository, branch, внешний сервис или другой постоянный state, проверить актуальный проект/target и соответствие действия текущей задаче.

**ЗАЧЕМ:**  
Предотвращает запись в неверный проект, файл, ветку или устаревший target из старого контекста.

**КОГДА ДЕЙСТВУЕТ:**  
Перед любым write-действием с постоянным эффектом.

**НЕ ТРЕБУЕТ:**  
Отдельного подтверждения пользователя перед каждым безопасным техническим действием, если разрешение уже есть.

**ИСТОЧНИК:**  
PROJECT-RISK / EXTERNAL-PRACTICE

---

## RULE-LIFECYCLE-001 — Одна фаза отвечает только за свою область

**ПРАВИЛО:**  
Каждая lifecycle-фаза меняет только свой канон. Если обнаруженная проблема принадлежит предыдущей фазе, использовать `RETURN_TO_PHASE` вместо молчаливого исправления чужого артефакта.

**ЗАЧЕМ:**  
Предотвращает скрытое изменение intent, требований или governance техническим решением.

**КОГДА ДЕЙСТВУЕТ:**  
Во всех фазах жизненного цикла проекта.

**НЕ ТРЕБУЕТ:**  
Повторять всю предыдущую фазу. Возврат должен исправлять только обнаруженную дыру.

**ИСТОЧНИК:**  
PROJECT-RISK / EXTERNAL-PRACTICE

---

## RULE-MINIMAL-001 — Не создавать сущности без конкретной пользы

**ПРАВИЛО:**  
Не создавать новый документ, реестр, gate, ADR, service, abstraction, dependency или process layer только «на будущее». Сначала должна быть конкретная проблема, которую существующие механизмы не закрывают проще.

**ЗАЧЕМ:**  
Проект маленький; лишняя инфраструктура быстро становится дороже самого конвертера.

**КОГДА ДЕЙСТВУЕТ:**  
При предложении новых постоянных сущностей или процессов.

**НЕ ТРЕБУЕТ:**  
Отказываться от новой сущности, если её необходимость доказана.

**ИСТОЧНИК:**  
PROJECT-RISK / EXTERNAL-PRACTICE

---

## RULE-GOV-001 — Правила меняются только по причине

**ПРАВИЛО:**  
Новое постоянное правило требует конкретного риска или обязательного свойства. Устаревшее правило удаляется или изменяется, а не обходится молча.

**ЗАЧЕМ:**  
Предотвращает превращение governance в набор исторических запретов и противоречий.

**КОГДА ДЕЙСТВУЕТ:**  
При изменении `03_PROJECT_RULES.md` или его будущих operational projections.

**НЕ ТРЕБУЕТ:**  
SemVer, голосований или отдельного amendment-процесса.

**ИСТОЧНИК:**  
PROJECT-RISK / EXTERNAL-PRACTICE

# PROJECT-SPECIFIC

## RULE-DATA-001 — Сохранность данных имеет абсолютный приоритет

**ПРАВИЛО:**  
Поддерживаемое текстовое и табличное содержимое Word нельзя молча потерять, изменить, округлить, обрезать, переинтерпретировать или заменить. Если точное безопасное преобразование невозможно, результат должен быть явно помечен предупреждением или ошибкой.

**ЗАЧЕМ:**  
Это главное подтверждённое свойство продукта. Excel, который выглядит корректно, но изменил данные, считается неправильным результатом.

**КОГДА ДЕЙСТВУЕТ:**  
При любой логике чтения Word, нормализации структуры, преобразования типов, записи XLSX и проверке результата.

**НЕ ТРЕБУЕТ:**  
Сохранять визуальное оформление Word один в один.

**ИСТОЧНИК:**  
USER / INTENT / SPEC

---

## RULE-DATA-002 — Рабочий Excel важнее визуального копирования Word

**ПРАВИЛО:**  
Если точное воспроизведение Word-структуры или оформления мешает обычной работе Excel, структура может быть нормализована при условии сохранения всех данных либо явного обозначения неоднозначности.

**ЗАЧЕМ:**  
Пользователю нужен рабочий Excel для сортировки, фильтрации, формул и сводных, а не визуальный снимок Word.

**КОГДА ДЕЙСТВУЕТ:**  
При сложных Word-таблицах, merged/split cells, нестандартной сетке и оформлении.

**НЕ ТРЕБУЕТ:**  
Уничтожать полезное оформление, если оно не мешает функциональности Excel.

**ИСТОЧНИК:**  
USER / INTENT / SPEC

---

## RULE-DATA-003 — Опасная автоматическая типизация запрещена

**ПРАВИЛО:**  
Нельзя автоматически превращать значение в число, дату или другой Excel-тип, если это может изменить исходное значимое содержимое. При конфликте между удобным типом и сохранностью выбирается сохранность.

**ЗАЧЕМ:**  
Excel может удалить ведущие нули, изменить отображение дат и потерять точность длинных цифровых последовательностей.

**КОГДА ДЕЙСТВУЕТ:**  
При преобразовании значений из Word в XLSX.

**НЕ ТРЕБУЕТ:**  
Хранить все значения как текст. Безопасная типизация разрешена, если не меняет значимое содержимое.

**ИСТОЧНИК:**  
SPEC / ANALOG_EVIDENCE

---

## RULE-DATA-004 — Исходный Word неизменяем

**ПРАВИЛО:**  
Конвертация не должна изменять исходный `.doc` или `.docx`.

**ЗАЧЕМ:**  
Источник данных должен оставаться доступным для повторной проверки и восстановления при ошибке.

**КОГДА ДЕЙСТВУЕТ:**  
При каждом запуске конвертации, успешном или ошибочном.

**НЕ ТРЕБУЕТ:**  
Создания резервной копии исходника, если сам исходник не изменяется.

**ИСТОЧНИК:**  
SPEC / PROJECT-RISK

---

## RULE-PORTABLE-001 — MVP не получает скрытых обязательных зависимостей

**ПРАВИЛО:**  
Нельзя вводить обязательную зависимость главного сценария от установленного Microsoft Word, Microsoft Excel, другого офисного пакета или активного интернета без возврата в owning requirements phase.

**ЗАЧЕМ:**  
Автономная portable-работа подтверждена как обязательное свойство MVP.

**КОГДА ДЕЙСТВУЕТ:**  
При выборе или изменении технического решения, которое влияет на runtime-требования пользователя.

**НЕ ТРЕБУЕТ:**  
Запрещать использование внешних инструментов в разработке и тестировании, если конечному пользователю они не нужны.

**ИСТОЧНИК:**  
USER / SPEC

---

## RULE-MVP-001 — Не включать отложенные функции в первую версию

**ПРАВИЛО:**  
OCR, пакетная обработка нескольких Word-файлов и универсальная офисная конвертация не входят в MVP, пока требования не изменены соответствующей фазой.

**ЗАЧЕМ:**  
Эти функции уже обсуждались и сознательно отложены.

**КОГДА ДЕЙСТВУЕТ:**  
При планировании, UX, техническом проектировании и реализации MVP.

**НЕ ТРЕБУЕТ:**  
Удалять архитектурные возможности расширения, если они не увеличивают scope и сложность текущего MVP.

**ИСТОЧНИК:**  
USER / SPEC

# REJECTED

- **Кандидат:** огромный универсальный `AGENTS.md`, содержащий всю спецификацию, архитектуру, историю и процессы.  
  **Почему не принят:** дублирует source of truth, расходует контекст и быстро устаревает.

- **Кандидат:** обязательный approval пользователя перед каждым техническим действием.  
  **Почему не принят:** создаёт процесс тяжелее риска; достаточно проверить write-target и иметь действующее разрешение.

- **Кандидат:** полный regression suite перед любым утверждением или небольшим изменением.  
  **Почему не принят:** уровень проверки должен соответствовать утверждению и риску.

- **Кандидат:** отдельные ADR/evidence/gate-файлы уже на старте проекта.  
  **Почему не принят:** пока нет конкретной проблемы, которую они решают дешевле существующих артефактов.

- **Кандидат:** отдельное обязательное security/secrets правило для MVP.  
  **Почему не принят:** текущий продукт локальный и не имеет подтверждённой работы с аккаунтами, токенами или секретами. Если такие зависимости появятся, риск должен быть пересмотрен.

# Source of Truth Map

- **Intent / зачем существует продукт:** `01_PROJECT_INTENT.md`
- **Product requirements / что обязан делать MVP:** `02_MVP_SPEC.md`
- **Permanent governance / постоянные правила:** `03_PROJECT_RULES.md`
- **UX decisions:** будущий `04_PRODUCT_UX_DESIGN.md`
- **Visual target:** будущий артефакт Фазы 05
- **Technical HOW:** будущий technical plan Фазы 06
- **Current implementation state:** живой код, файлы и repository state
- **Verification evidence:** свежие test results, команды, сравнения входа/выхода и другие проверяемые результаты
- **Handoff:** указатель на завершённую работу и следующую фазу; не заменяет проверку source of truth
- **Старая память / старый чат:** вспомогательный контекст, который не перебивает более свежий проверяемый источник

При конфликте между «что должно быть» и «что сейчас реализовано» расхождение фиксируется явно. Требование не меняется потому, что текущий код реализован иначе.

# Governance / Agent-Rules Prior Art

## Источник 1 — OpenAI Codex / AGENTS.md

**Источник:**  
OpenAI — Introducing Codex; Unrolling the Codex agent loop.

**Практика:**  
Agent-инструкции могут иметь scope по дереву директорий; более конкретные инструкции применяются к соответствующим областям. После изменений должны выполняться релевантные программные проверки, если они заданы.

**Что взяли:**  
- scope инструкции должен быть явным;
- runtime-инструкции должны соответствовать фактической рабочей среде;
- проверка результата должна соответствовать изменению.

**Что НЕ взяли:**  
- конкретный Git workflow, branch policy и commit policy из примеров OpenAI.

**Почему:**  
Они относятся к конкретной среде выполнения, а не к постоянному governance этого проекта.

## Источник 2 — OpenAI Harness Engineering

**Источник:**  
OpenAI — Harness engineering: leveraging Codex in an agent-first world.

**Практика:**  
Короткий `AGENTS.md` используется как карта к структурированным источникам истины; большой монолитный файл инструкций создаёт stale context и расходует контекст агента.

**Что взяли:**  
- runtime-инструкции должны быть короткой картой;
- глубокий канон хранится в соответствующих source-of-truth документах;
- не дублировать всё в одном файле.

**Что НЕ взяли:**  
- конкретную структуру docs/ и внутренние процессы OpenAI.

**Почему:**  
Проект значительно меньше; копирование инфраструктуры крупного проекта нарушило бы принцип минимальности.

## Источник 3 — GitHub Copilot custom instructions

**Источник:**  
GitHub Docs — Adding repository custom instructions.

**Практика:**  
GitHub разделяет repository-wide, path-specific и agent instructions; path-specific правила применяются только к соответствующей области.

**Что взяли:**  
- будущая operational projection должна учитывать scope;
- локальные инструкции не должны перегружать глобальные правила.

**Что НЕ взяли:**  
- конкретный формат `.github/copilot-instructions.md` как обязательный.

**Почему:**  
Runtime-среда будет выбрана позже; Фаза 03 создаёт канон, а не vendor-specific конфигурацию.

## Источник 4 — GitHub Spec Kit

**Источник:**  
GitHub — `github/spec-kit`.

**Практика:**  
Проектные принципы, product specification, technical plan, tasks и implementation разделяются на разные этапы.

**Что взяли:**  
- не смешивать governance с product spec и technical HOW;
- каждая фаза меняет только свою область;
- технические решения не должны незаметно переписывать требования.

**Что НЕ взяли:**  
- полный workflow и набор артефактов Spec Kit.

**Почему:**  
Наш lifecycle уже определён и должен оставаться минимальным.

# Подтверждено

- Пользовательский intent и MVP-spec согласованы.
- Главный приоритет продукта — сохранение данных и получение рабочего Excel.
- Молчаливая потеря или изменение поддерживаемых данных недопустимы.
- Сложная структура Word может нормализоваться.
- Visual fidelity Word не имеет приоритета над рабочей Excel-структурой.
- Исходный Word не должен изменяться.
- MVP должен работать без обязательного Word, Excel и интернета.
- Один Word-файл обрабатывается за один запуск.
- `.doc` и `.docx` обязательны.
- OCR и пакетная обработка отложены.

# Обнаружено

- OpenAI рекомендует использовать agent-инструкции как короткую карту к более глубоким source-of-truth материалам вместо монолитного файла.
- OpenAI Codex и GitHub поддерживают scoped agent/repository instructions.
- GitHub Spec Kit разделяет governing principles, specification, technical plan и implementation tasks.
- Эти практики поддерживают выбранный подход: небольшой постоянный канон + последующие runtime-specific projections.

# Гипотезы

- Значительную часть `RULE-DATA-*` можно будет позже обеспечить автоматическими тестами и валидаторами.
- Одного repository-wide runtime instruction file может оказаться достаточно; необходимость nested/path-specific инструкций пока не доказана.
- Отдельный security/secrets governance станет нужен только если будущий technical plan введёт реальные секреты или внешние сервисы.

- Конкретная структура репозитория.
